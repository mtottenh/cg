_Generated 2026-07-19. Investigation-only pass across both repos (backend `api/`, frontend `web/`) plus the `deploy/` Ansible scaffolding. Produced by an 8-area parallel audit with adversarial verification of every Critical/High finding; all four Critical findings were additionally re-verified by hand against the cited code. This file is intentionally uncommitted._

Backend (api repo, commits `ddf0f0f`, `7a60aba`, `e32a210`, `4318899`): Steam takeover guard + `@steam.invalid` rejection, end-to-end platform-ban enforcement, refresh status gate, status-guarded claim confirms + saga-dedupe migration 0068, persisted admin/dispute progression standings, and `auto_confirm_at` wired into the lifecycle loop — full suite green, clippy/fmt clean. ## Overall verdict: **Not ready** → **Ready-with-conditions** (post-remediation; pending a staging dry-run)

The application code is broadly well engineered (auth machinery, RBAC, graceful shutdown, SQL hygiene, and CI all verified good), but the platform cannot be launched as-is for three independent reasons. First, the deploy tooling literally cannot ship the product today: the prod env template omits the Steam URLs so login redirects to localhost for the 89/90 Steam-only users, Caddy serves an empty /var/www/portal because no frontend build/ship step exists, the scanner and demo-stats roles are missing or unwired, and the inventory/vault are all CHANGE_ME placeholders. Second, two CONFIRMED Critical security defects — a pre-registration Steam account-takeover via the reserved @steam.invalid email and a ban system that is never enforced anywhere (compounded by refresh tokens that ignore account status) — mean the platform can neither protect accounts nor remove abusive users. Third, CONFIRMED High correctness bugs (double-counted standings on concurrent claim confirms, admin/dispute progression that never persists standings, auto-confirm deadlines that never fire) silently corrupt or stall the core tournament product. All are fixable within a focused two-week runway, after which a re-verification pass should move the verdict to Ready-with-conditions.

## Executive summary

This audit found a codebase whose engineering fundamentals are genuinely strong — JWT lifecycle with HS256 pinning and per-request RBAC re-checks, refresh-token rotation with replay detection, uniformly parameterized SQL, SSRF-guarded outbound calls, a dev-token bypass provably compiled out of release builds, graceful shutdown done correctly, 548 real integration tests, and a prior RBAC audit that held up under adversarial re-verification. However, it is not launchable today. The deployment scaffolding has never converged against a real host and would ship a broken product: Steam sign-in (the only login path for ~99% of migrated users) redirects to localhost because PORTAL_PUBLIC_URL/PORTAL_FRONTEND_URL/STEAM_API_KEY are absent from api.env.j2; Caddy serves an empty docroot because no frontend build/ship step exists; the `just deploy` scanner tag matches zero tasks; the demo-stats role is not in site.yml; and the inventory/vault are placeholder-only.

On top of the deployment gaps, adversarial verification CONFIRMED two Critical security defects and a cluster of High correctness bugs. An attacker can pre-register a local account with email steam_<victim_id64>@steam.invalid and silently capture the victim's first Steam sign-in; bans created through the admin API write a table nothing reads, and token refresh never checks account status, so the platform cannot effectively remove a user. In the tournament core, concurrent claim confirms double-run the completion saga and double-count standings, the admin/dispute progression path computes standings in memory and never persists them, the advertised auto_confirm_at deadline is wired to nothing, and the frontend's 401 refresh-retry replays mutations with an empty body, breaking the idle-then-submit path. The good news: every blocker has a concrete, verified fix, most are S/M effort, and the two-week plan below sequences security and correctness fixes in week 1 and deployment completion plus a full staging dry-run in week 2. Dependency exposure was largely defanged on verification (the scary Cargo advisories are dead code or unreachable), needing only a cheap `cargo update` + `npm audit fix` pass.

## Launch blockers

These must be fixed before real users. Severity and evidence below were confirmed under adversarial verification.

### 1. [Critical] Steam sign-in recovery allows pre-registration account takeover via reserved @steam.invalid email

- **Area:** Correctness / account provisioning
- **Evidence:** CONFIRMED: crates/portal-domain/src/services/user.rs:267-274 falls back to find_by_email("steam_<id64>@steam.invalid") and recovers whatever user owns that email with no auth_provider or status check; registration accepts that email format (dto/requests/auth.rs:31, migrations/0001_create_users.sql:55-57). An attacker who pre-registers with a victim's public SteamID64 gets the victim's first Steam sign-in linked to the attacker's password-controlled account.
- **Fix (S):** In the email-recovery branch require user.auth_provider == "steam" and status == Active before recovering; additionally reject registration/update emails ending in @steam.invalid. Add a regression test for the takeover scenario.

### 2. [Critical] Bans issued via the admin API are never enforced anywhere

- **Area:** Authentication and Authorization
- **Evidence:** CONFIRMED: POST /v1/admin/bans (handlers/bans.rs:145) only inserts into the bans table; BanService::is_user_banned (services/ban.rs:100-102) has zero production callers; login checks only users.status (services/user.rs:421-426, 234-239), which only the CLI sets. Eligibility/registration never consult bans. The admin UI reports the ban as active while the user retains full access.
- **Fix (M):** Make BanService::create_ban (platform bans) set users.status='banned' and revoke all refresh tokens, mirroring the CLI path; lift_ban must restore status. Add an integration test: create ban via API, assert login and refresh both fail.

### 3. [Critical] Steam auth URLs and API key absent from prod env template — Steam login redirects to localhost

- **Area:** Deployment and configuration
- **Evidence:** CONFIRMED: deploy/ansible/roles/portal_api/templates/api.env.j2 sets none of PORTAL_PUBLIC_URL/PORTAL_FRONTEND_URL/STEAM_API_KEY; steam_openid.rs:51-55 defaults to http://localhost:3000 / :5173. Per docs/deployment-cs210mans-audit.md, 89/90 migrated users are Steam-auth only — a deploy from this template ships with authentication broken for essentially the entire user base.
- **Fix (S):** Add PORTAL_PUBLIC_URL=https://{{ portal_domain }}, PORTAL_FRONTEND_URL, and STEAM_API_KEY={{ vault_steam_api_key }} to api.env.j2; add the vault slot to vault.example.yml; optionally refuse to serve /auth/steam/* when public_url is still the localhost default in release builds.

### 4. [Critical] No frontend build/ship step — Caddy serves an empty /var/www/portal

- **Area:** Deployment and configuration
- **Evidence:** CONFIRMED: roles/caddy/tasks/main.yml:31-37 creates an empty docroot that no role populates; deploy/README.md admits the gap; `just deploy` ships only debs. Related (Med, verified): web/.env is committed with VITE_API_URL=http://localhost:3000 and client.ts:5/uploadUrl.ts:16/steamAuth.ts:40/useMatchLobbySocket.ts:4 fall back to localhost, so even a naive build would bake dev URLs into the bundle.
- **Fix (M):** Add a portal_web role (build with VITE_API_URL=https://{{ portal_domain }}, rsync dist/ to /var/www/portal) wired into site.yml, or build in CI and ship the artifact. Untrack web/.env, add .env.production, and make client.ts fail fast in PROD when VITE_API_URL is unset.

### 5. [High] Token refresh never checks account status — banned/suspended users keep sessions alive indefinitely

- **Area:** Authentication and Authorization
- **Evidence:** CONFIRMED: refresh handler (handlers/auth.rs:195-291) uses a bare find_by_id with no status gate (services/user.rs:88-93) and re-issues a fresh 7-day refresh token; revoke_all_for_user's only production call site is replay detection (auth.rs:226). Even a CLI-banned user retains access forever by rotating tokens.
- **Fix (S):** Reject refresh when user.status != Active and revoke the token chain; call revoke_all_for_user from every ban/suspend path so residual access is capped at the 15-minute access-token window.

### 6. [High] Concurrent claim confirms double-run the completion saga and double-count round-robin/swiss standings

- **Area:** Correctness and data integrity
- **Evidence:** CONFIRMED end-to-end: is_pending check outside any tx (services/tournament/result.rs:191-198), unguarded UPDATE (adapters/tournament/result_claim.rs:282-301), no saga dedupe on match_id (saga.rs:129-163; live DB shows no unique index), non-idempotent `points = points + $8` deltas (standings.rs:86-94). A double-click gives the winner +6 points and 2 wins; the same unguarded pattern enables a confirm/dispute race.
- **Fix (M):** Add `AND status = 'pending'` to the claim UPDATEs and return Conflict on 0 rows; add a partial unique index on saga_executions(match_id, saga_type) WHERE status IN ('running','paused') or check for an existing saga before start_saga.

### 7. [High] Admin/dispute-reapply progression computes standings in memory and never persists them

- **Area:** Correctness and data integrity
- **Evidence:** CONFIRMED: progression.rs:326-383 mutates the in-memory Vec and only calls recalculate_positions, which re-ranks unchanged stored points (standings.rs:116-147); the API response returns standings the DB does not contain. Live on POST /v1/admin/matches/{id}/progression/{process,reapply}; can seed playoffs from stale points via advance_to_next_stage.
- **Fix (M):** Replace the in-memory mutation with the delta-based standings_repo.update_after_match calls the saga path uses (match_completion.rs:1018-1050), or route the admin endpoints through MatchCompletionService so there is one progression implementation. Add tests for the admin revert/reapply/process endpoints (currently zero direct coverage).

### 8. [High] Result-claim auto-confirmation wired to nothing — auto_confirm_at deadlines never fire, brackets stall

- **Area:** Correctness and data integrity
- **Evidence:** CONFIRMED: process_auto_confirmations (result.rs:344-362) has zero call sites; the background loop handles only check-in/veto/no-show/evidence (background/mod.rs:114-189); auto_confirm_at is computed and returned to clients on every submit (result.rs:148) but never enforced. A claim the opponent ignores stays pending forever without admin intervention — and the admin recovery path has the standings bug above.
- **Fix (S):** Add an auto-confirm pass to run_lifecycle_pass that calls process_auto_confirmations then executes the completion saga for each confirmed claim (auto_confirm_claim currently never advances the bracket either). Cover with a lifecycle_automation integration test.

### 9. [High] Frontend 401 refresh-retry re-sends mutations with a consumed (empty) body

- **Area:** Frontend
- **Evidence:** CONFIRMED and empirically reproduced: web/src/api/middleware/errorMiddleware.ts:66-71 retries with `body: request.bodyUsed ? undefined : request.body`; openapi-fetch passes the already-sent Request to onResponse, so bodyUsed is always true. Every POST/PUT/PATCH issued after access-token expiry is retried body-less and rejected 400/422 — the classic user-idles-then-submits-a-form path is systematically broken.
- **Fix (S):** Capture a replayable body copy in an onRequest hook (request.clone() before send) and build the retry from it; add a unit test that a POST retried after refresh carries its original JSON body.

### 10. [High] Forward-only migrations auto-run on deploy with no pre-migration backup — up to 24h data-loss window

- **Area:** Reliability and Operations
- **Evidence:** CONFIRMED: 67 forward migrations, zero down migrations; migrations run unconditionally at startup (portal-app/src/main.rs:35); `just deploy` restarts the service with no dump first; the only backup is the nightly 03:15 pg_dump timer, no PITR, and zero restore runbook or restore verification anywhere in deploy/.
- **Fix (S):** Add `systemctl start pg-backup.service` (and wait) as a pre_task on the portal_api role or in the deploy recipe so every deploy has a seconds-old restore point; write and test a restore runbook against a scratch DB.

### 11. [High] justfile deploys a portal_scanner role that does not exist — scanner silently never installed

- **Area:** Deployment and configuration
- **Evidence:** CONFIRMED: deploy/justfile:36-38 passes --tags portal_scanner and downloads the deb, but no roles/portal_scanner exists and site.yml lists only base/postgres/portal_api/caddy/backups; Ansible silently matches zero tasks and `just deploy` exits 0. Nothing renders the /etc/portal/scanner.env the README claims.
- **Fix (M):** Create roles/portal_scanner (deb install + scanner.env template with PORTAL_API_KEY from vault, SCANNER_GAME_ID, S3 and service URLs — the binary .expect()-panics without them) and add it to site.yml.

### 12. [High] Demo-stats pipeline dead in prod: role not in site.yml, CS2_DEMO_SERVICE_URL never set, no Caddy front

- **Area:** Deployment and configuration
- **Evidence:** CONFIRMED: roles/portal_demo_stats exists but site.yml never runs it; api.env.j2 has no CS2_DEMO_SERVICE_URL so the plugin silently registers without a demo backend (state/mod.rs:415-418); the SSRF guard requires an https non-private URL but Caddyfile.j2 has no demos.* site block; the two vault_demo_stats_s3_* keys are absent from vault.example.yml.
- **Fix (M):** Add portal_demo_stats to site.yml, a demos.{{ portal_domain }} Caddy block proxying 127.0.0.1:3100, CS2_DEMO_SERVICE_URL=https://demos.{{ portal_domain }} in api.env.j2, and the two vault keys to vault.example.yml.

### 13. [High] Inventory and vault are placeholder-only — the deploy has never converged against a real host

- **Area:** Deployment and configuration
- **Evidence:** CONFIRMED: inventory/prod.yml has ansible_host: CHANGE_ME, portal.example.com, ops@example.com; all five vault_* secrets in vault.example.yml are CHANGE_ME with no encrypted vault.yml ever committed; site.yml asserts only jwt_secret length, so four of five placeholders pass validation. The prior audit's secret-rotation items (plaintext Linode + Steam keys on the old box) remain open.
- **Fix (S):** Set the real host/domain/ACME email, create an encrypted vault.yml with rotated Linode and Steam keys, extend the site.yml assert to reject any CHANGE_ME value, then run a full staging convergence before cutover.

## Findings by area

### Authentication and Authorization

Core auth machinery is well built: JWTs are HS256-pinned with 15-minute expiry and deliberately carry no role/admin claims (every authz decision re-checks the RBAC tables per request via PermissionChecker), refresh tokens are 32-byte random values stored SHA-256-hashed with rotation, replay detection (revoke-all-on-reuse) and race-safe consumption, the Steam OpenID callback verifies assertions directly with Steam (check_authentication + is_valid:true), validates openid.return_to against the deployment and restricts claimed_id to steamcommunity.com, and the dev-token bypass is provably compiled out of release builds (cfg-gated, feature not default, not enabled by portal-app or the Dockerfile). The rbac-audit-2026-07-19.md fixes all held up under spot-checking (roles priority ceiling, forfeit ownership, tournament scoped permissions, dispute participant binding). However, the ban/suspension enforcement story is broken end-to-end: bans created through the admin API write only the bans table which no authentication or authorization path ever reads (BanService::is_user_banned has zero callers), and the token refresh endpoint never checks user status, so even a user whose users.status was set to banned via the CLI keeps a valid session indefinitely by rotating refresh tokens. These two together mean the platform currently cannot effectively ban an active user, which is a launch blocker.

### Correctness and data integrity (backend: migrations, constraints, races, account provisioning)

DB-level integrity is mostly solid: all 67 migrations apply cleanly in order, destructive changes (0024 UUID restructure, 0054 api_key permissions) carry proper backfills, and the important invariants (unique username/email, unique steam_id_64, one player per user, award scope/name and podium uniqueness, one demo-match link, one registration per team/player per tournament) are enforced by real constraints verified against the live dev DB. The recent I5 remediation genuinely made claim submit, claim confirm+match-apply, and dispute-raise atomic. However, the concurrency story above the DB has holes: the claim-confirm UPDATE carries no status guard and the saga layer has no dedupe, so two concurrent confirms double-run the completion saga and double-increment round-robin/swiss standings (non-idempotent `points = points + $8` deltas); the admin/dispute-reapply progression path computes standings deltas in memory and never persists them; and the auto-confirm sweep exists but is wired to nothing, so auto_confirm_at deadlines are never enforced. Worst finding: the Steam sign-in partial-account recovery branch matches on the deterministic `steam_<id64>@steam.invalid` email without checking auth_provider, and nothing stops a local registration from claiming that email first — a pre-registration account-takeover vector. The steam-side partial-account recovery itself (recover_partial_steam_account) is otherwise correct and idempotent; the local register path has no equivalent recovery and can permanently brick a username/email on partial failure.

### Reliability and Operations

Graceful shutdown is genuinely well done: portal-app installs SIGINT+SIGTERM handlers, drains in-flight requests via axum's with_graceful_shutdown, signals both background loops over a shared Notify, awaits their JoinHandles with a 10s bound, and closes the pool (crates/portal-app/src/main.rs:97-141). Health endpoints really do probe dependencies (SELECT 1 for DB on both /health and /health/ready; demo-service reachability reported as degraded-but-ready), verified against the live dev API. Request IDs are server-generated, injected into the tracing span, echoed on responses and DTO meta. The deploy repo has systemd supervision (Restart=on-failure) and a nightly pg_dump-to-S3 backup timer. The main reliability gaps: the two background loops have no panic supervision (a panic silently kills tournament automation until the next process restart, with no health/metric signal), migrations are forward-only with no pre-deploy backup step so rollback means restoring an up-to-24h-old dump, the prod binary runs with the 10-connection default pool (the production() preset is dead code and nothing is env-tunable), logs are plain-text despite the systemd unit claiming JSON support, and there is no metrics endpoint at all.
